Why Nano BPM

Nano BPM is an advanced research prototype — a BPMN orchestration engine written from first principles in Rust to explore what becomes possible without the JVM stack: how fast execution can get, how small the footprint can be (it even compiles to WASM and runs in a browser), and how a process engine can auto-scale without collapsing under load. It speaks a Camunda-compatible API so it can reuse the existing tooling ecosystem and be measured against a mature engine. It is a research prototype — a place to explore ideas, not a production system.

Extremely low resource

Written from first principles in Rust for high performance under tight resource constraints. No JVM, no garbage collector, no external database, no container orchestra — one statically linked binary.

The execution engine (engine-core) is a zero-dependency Rust crate. Everything around it — gateway, REST API, Falcon protocol, web console, modeler, explorer, embedded workers, Swagger UI and Prometheus metrics — ships inside the same binary. There is nothing else to install, no Elasticsearch, no relational database, no message broker.

Compiles to WASM — runs in a browser or on a phone

Because the engine core has no platform dependencies it builds cleanly for wasm32-unknown-unknown and embeds into native mobile apps over a thin FFI layer. The same orchestration engine that runs the server can run inside a web page or on an iPhone/Android device — offline-capable process execution at the edge, not just in a data centre.

Memory stays flat and predictable: a fully loaded single node sustaining ~27,800 instances/s holds a working set well under 100 MB. Idle worker connections cost ~0.15–0.2 MB each (linear, no surprises), and jemalloc is configured to return idle pages to the OS so the process shrinks back down between bursts.

High performance and durable

A single-writer-per-partition engine with a group-commit write-ahead log, optional per-partition Raft replication, and a measured single-node ceiling far above a default Camunda deployment on the same hardware.

HA / FT multi-node clustering Raft RF=3

Every partition is its own Raft group. Writes commit only on quorum acknowledgement, and leadership fails over automatically when a node dies — serving (creates, job activation, completion, reads) follows the new leader without client intervention.

  • Quorum-committed writes — a client-acked command survives node loss (replicated to a majority before ack).
  • Fast failover — ~1 ms re-election in chaos tests; in-flight forwards bounded so a frozen leader can’t stall the cluster.
  • At-least-once preserved across failover — a job leased on the killed leader re-activates on the new leader (verified end-to-end).
  • Any node is a gateway — a client connected to one node addresses the whole cluster (create placement, by-key mutations, cross-node job aggregation, reads all forward to the owning leader).

Durability model

All partitions funnel through one shared group-commit WAL writer (one file, one fsync stream) so concurrent commands coalesce into a single fsync — no per-partition fsync fragmentation. Two tiers are selectable per deployment:

  • sync (default) — ack after the fsync; a client-acked command is on stable storage.
  • async — ack after the page-cache write with amortized fsync; ~2× throughput and ~3× lower latency for open-loop producers, surviving process crash via replay.

Under Raft, the replicated log becomes the durable tier and commit = quorum-ack; bounded state-based snapshots keep replica memory in check.

Dynamic client/server architecture

Workers attach over a bidirectional Falcon protocol and pull work via a credit window. The server meters intake to match capacity, so adding workers — even far more than you need — never tips the system into collapse.

Auto-scaling job stream — no over-provisioning collapse

On the Falcon transport, each worker subscription has a credit window; the server grants credits and emits an explicit back-pressure signal (Pressure red/green) instead of dropping requests. The result: clients self-pace, in-flight work is bounded, and latency stays flat regardless of how over-provisioned the fleet is.

Camunda-compatible API surface

Nano implements the Camunda Orchestration Cluster REST API and the Falcon protocol. That compatibility is a research lever: it lets Nano reuse the existing SDKs and tooling, and be evaluated head-to-head against a mature engine — without re-inventing a client ecosystem.

  • Same REST API surface — the gateway serves the Camunda Orchestration Cluster REST API (browse all operations in the built-in Swagger UI).
  • Existing SDKs work against it — applications using the Camunda enhanced SDKs can point at a Nano cluster, which makes it easy to drive the engine with real client code while experimenting.
  • Speaks the Falcon protocol — because those SDKs use the Falcon protocol, they exercise Nano’s auto-scaling job-stream path directly — a convenient way to study that architecture under realistic load.
  • Execution semantics — Nano follows Camunda execution semantics and explores capabilities on top (e.g. embedded workers, idempotent deployment, in-engine BPMN XML retention).
A research vehicle, not a migration target. Because the API and protocol match, you can point existing Camunda SDKs and models at a Nano cluster to experiment with the engine — a low-friction way to explore what it does, not a recommendation to run production workloads on a research prototype.

More that’s built in

Capabilities that usually mean extra services, sidecars or a separate tool — included in the one binary.

  • Embedded web console — live topology, process explorer with a BPMN token view, modeler, worker editor and a metrics dashboard, served at /console.
  • Embedded workers — author job workers in TypeScript (Node runtime), use npm libraries, run them headless inside the platform — no separate worker deployment.
  • Idempotent deployment — redeploying a byte-identical model is a no-op; it does not mint a new version.
  • Prometheus metrics + cluster dashboard — throughput, active instances, connected workers, per-node memory and health, on /metrics and in the console.
  • Open Falcon protocol — the same bidirectional WebSocket protocol powers SDK workers, in-browser workers and inter-node forwarding.
  • Offline & self-contained — the console, Swagger UI and this page load zero external assets; everything works air-gapped.
